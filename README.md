# Office Inventory

Вебзастосунок для обліку видачі спільних речей в офісі: ноутбуків, проєктора, камери, павербанків, настільних ігор, парасоль. Замінює Google Sheets: видно, що де лежить, у кого річ і коли її повернуть, що прострочено, а що в ремонті.

## Стек

- **Backend:** Node.js 22.13+, Express 5, TypeScript, SQLite (вбудований `node:sqlite`), Zod
- **Frontend:** React 19, Vite, TypeScript, Mantine, TanStack Query, React Router
- **Тести:** Vitest, Supertest
- **Інструменти:** npm workspaces, Prettier, EditorConfig

## Запуск

Потрібен **Node.js 22.13 або новіший** (рекомендовано 24 LTS, див. `.nvmrc`).

```bash
npm run setup   # встановлення залежностей + створення БД з демо-даними
npm run dev     # сервер (http://localhost:3000) і клієнт (http://localhost:5173)
```

Відкрийте **http://localhost:5173**.

Демо-дані згенеровано відносно поточної дати, тому на головній завжди є прострочені видачі, видачі "на сьогодні/завтра" та речі в ремонті. Щоб повернути БД до початкового стану: `npm run db:seed -w server`.

## Структура проєкту

```
office-inventory/
├── server/                      # REST API
│   ├── src/
│   │   ├── app.ts               # збирання застосунку: модулі, роути, обробка помилок
│   │   ├── index.ts             # точка входу: БД + запуск сервера
│   │   ├── config/env.ts        # змінні оточення з валідацією
│   │   ├── db/                  # підключення, міграції, транзакції, seed
│   │   ├── errors/              # AppError: помилка зі статусом і кодом
│   │   ├── middleware/          # 404 і централізована обробка помилок
│   │   ├── modules/
│   │   │   ├── items/           # речі: schemas → repository → service → router
│   │   │   ├── loans/           # видачі та повернення
│   │   │   ├── employees/       # співробітники (лише читання)
│   │   │   └── dashboard/       # зведення для головної сторінки
│   │   └── utils/date.ts
│   └── tests/                   # API- та unit-тести
└── client/                      # React SPA
    └── src/
        ├── api/                 # типи, HTTP-клієнт, хуки TanStack Query
        ├── app/router.tsx
        ├── components/          # спільні компоненти й модалки
        ├── pages/               # Головна, Речі, Картка речі, На руках
        └── utils/               # форматування дат, тексти помилок
```

Кожен серверний модуль має однакові шари:

- **schemas** - валідація вхідних даних (Zod);
- **repository** - лише SQL;
- **service** - бізнес-правила;
- **router** - HTTP.

Клієнт ходить на `/api` через proxy у Vite, тому CORS не потрібен.

## API

| Метод    | Шлях                    | Опис                                                    |
| -------- | ----------------------- | ------------------------------------------------------- |
| `GET`    | `/api/items`            | список речей; фільтри `q`, `category`, `state`          |
| `GET`    | `/api/items/categories` | наявні категорії                                        |
| `GET`    | `/api/items/:id`        | річ із поточною видачею                                 |
| `POST`   | `/api/items`            | створити річ                                            |
| `PATCH`  | `/api/items/:id`        | змінити річ                                             |
| `DELETE` | `/api/items/:id`        | видалити (архівувати) річ                               |
| `GET`    | `/api/employees`        | співробітники                                           |
| `GET`    | `/api/loans`            | видачі; фільтри `itemId` (історія речі), `active`       |
| `POST`   | `/api/loans`            | видати річ                                              |
| `POST`   | `/api/loans/:id/return` | повернути річ (зі станом: справна / ремонт / загублена) |
| `GET`    | `/api/dashboard`        | що потребує уваги                                       |

Річ у відповіді містить обчислене поле `state` (`available` | `on_loan` | `in_repair` | `lost`) і поточну видачу `currentLoan` з прапорцем `isOverdue`. Видача містить `note` (примітка при видачі), `returnNote` (примітка при поверненні) та `isOverdue`.

Помилки мають єдиний формат: `{ "error": { "code": "ITEM_ALREADY_ON_LOAN", "message": "..." } }`, статуси 400 / 404 / 409 / 413.

## Бізнес-правила

- Річ може мати лише одну активну видачу (перевірка в сервісі + частковий унікальний індекс у БД).
- Видати можна лише справну річ: не на руках, не в ремонті й не загублену.
- Термін повернення - від сьогодні до року вперед.
- При поверненні обирається стан речі: справна, потребує ремонту або загублена.
- Річ, яка зараз на руках, не можна видалити чи перевести в ремонт або "загублено" через редагування.
- Видалення - це архівування: історія видач зберігається.
- Інвентарний номер унікальний без урахування регістру (`LT-001` і `lt-001` - один номер).
- Прострочення обчислюється сервером: термін минув, а річ не повернута.

## Перевірка API (Postman)

У `docs/office-inventory.postman_collection.json` лежить колекція з 34 запитами та 75 автоматичними перевірками: успішні сценарії, помилки валідації (400), відсутні ресурси (404) і порушення бізнес-правил (409).

1. `npm run db:seed -w server` і `npm run dev`. Перевірки розраховані на демо-дані.
2. Postman → **Import** → файл колекції.
3. **Run collection** (без environment).

Запити виконуються послідовно: "Create item" і "Issue item" зберігають `id` для наступних кроків.

## Що не встигла

- **Керування співробітниками в інтерфейсі.** Список задається через seed, як дозволяє завдання.
- **Продовження терміну видачі.** Зараз для цього треба повернути річ і видати знову.
- **Автентифікація й ролі.** Застосунок розрахований на одну офіс-менеджерку.
- **Пагінація та пошук на рівні БД.** Для ~100 речей фільтрація в памʼяті достатня (див. DECISIONS.md).
- **Тести клієнта** (компоненти, e2e). Сервер покрито тестами бізнес-правил і колекцією Postman.
- **ESLint** і прогін колекції Postman у CI через Newman.
- **Сповіщення** про прострочені видачі (email/Slack).
- **Імпорт даних** з наявної Google-таблиці.
- **Розбиття бандла клієнта** (Vite попереджає про розмір чанка).
